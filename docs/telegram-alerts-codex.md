# Задание Codex — оповещения в Telegram не доходят никуда

Проект: Travel Time (Next.js + Supabase). Шахматка для менеджеров: часть отелей
менеджеры ведут вручную, часть («голубые») подтягивает занятость из чужих систем.
Сбои синхронизации должен ловить робот и писать в чат менеджеров.

Ветка отсчёта: `main`, коммит `0af3cf7`. Разбор чатов лежит в PR #78 (черновик).

**Токены и ключи не публиковать.** Репозиторий публичный, журналы Actions видны
всем. Номера чатов в вывод не печатать — только названия чатов и логины ботов.

---

## ЧТО УЖЕ УСТАНОВЛЕНО — НЕ ПЕРЕПРОВЕРЯТЬ ЗАНОВО

Каждый час падает `Sync Freshness`, каждый запуск падает `Telegram Chat Check`.
Причина одна: тревогу некуда отправить.

Прогон `Telegram Chat Check` 12.09.2026 (ветка `claude/keen-galileo-k10y9c`):

```
=== БОТ: Чат отельеров парс @abhazbereg_parsbot ===
Запись 1: НЕ ПОХОЖЕ НА ID: в секрет попал текст, ссылка или опечатка
=== ДЛЯ СРАВНЕНИЯ: чат карточки брони ===
  ✗ Telegram отказал: Bad Request: chat not found
Всего записей: 1, чатов доступно боту: 0
```

Отсюда два факта:

1. В секрете `TELEGRAM_MANAGER_CHAT_IDS` лежит **не номер чата** — текст, ссылка
   или обрывок. Не «устаревший id», а мусор: искать там правильный номер незачем,
   запись надо заменить целиком.
2. Бот за секретом `TELEGRAM_BOT_TOKEN` — **@abhazbereg_parsbot «Чат отельеров
   парс»**, и он не достучался **и до чата карточки брони** (`vars.TELEGRAM_BOOKING_CHAT_ID`).
   Значит либо в секрете токен не того бота, либо бота удалили изо всех чатов.

Побочное следствие, которое ещё никто не проверял вживую: отправка ваучеров и
`#бронь` из карточки брони (`.github/workflows/telegram-send-file.yml`,
`supabase/functions/telegram-bot`) идёт тем же токеном — скорее всего она тоже
не работает.

Что уже сделано и переделывать не надо:

- `scripts/telegram-chat-check.py` — разбор различает пять видов записи в секрете
  (id супергруппы / id обычной группы / личный чат / `@логин` / мусор), для обычной
  группы сам проверяет гипотезу о повышении до супергруппы, называет логин бота.
  13 тестов на подставных ответах Telegram, включая проверку, что ни один номер
  не попадает в вывод. Запуск: `npm run chat-check:test`.
- `scripts/check-sync-freshness.mjs` — при отказе доставки печатает логин бота.
  Инциденты, которые не удалось доставить, не помечаются оповещёнными и уходят
  повторно. Это сделано осознанно, менять нельзя.
- `Sync Freshness` падает, когда доставить не удалось ни в один чат. Это тоже
  осознанно: молчаливый зелёный прогон означал бы, что тревога растворилась.

## ЧТО ДОЛЖЕН СДЕЛАТЬ ЧЕЛОВЕК — АГЕНТ ЭТОГО НЕ МОЖЕТ

Секреты GitHub из кода не читаются и не меняются; добавить бота в чат Telegram
может только участник чата. Эти три шага — за Дарьей:

1. Убедиться, что нужный бот состоит в чате менеджеров.
2. Написать в чате `/chatid` — бот ответит номером (обработчик уже есть в
   `supabase/functions/telegram-bot/index.ts`, отвечает в любом чате).
3. Вписать номер в секрет `TELEGRAM_MANAGER_CHAT_IDS`
   (Settings → Secrets and variables → Actions).

Задача Codex — сделать так, чтобы после этих трёх шагов всё заработало с первого
раза, и чтобы такая поломка больше не тянулась неделями незамеченной.

## ЗАДАЧА 1. Выяснить, какой бот правильный

Сейчас токенов как минимум два и они могут расходиться:

- секрет GitHub `TELEGRAM_BOT_TOKEN` — им пользуются `Sync Freshness`,
  `Telegram Chat Check`, `telegram-send-file.yml`;
- секрет Supabase `TELEGRAM_BOT_TOKEN` — им пользуется Edge Function
  `telegram-bot` (она же отвечает на `/chatid` и на запросы менеджеров).

Надо установить, **один это бот или разные**, и какой из них реально сидит в чате
менеджеров и в чате карточки брони. Сравнивать по `getMe` → `username`; сами
токены никуда не печатать и в отчёт не выносить.

Результат задачи: короткий ответ в отчёте — «бот один, зовут @…» либо «ботов два,
@… и @…, в чатах сидит такой-то, в секрете GitHub лежит не тот».

Если окажется, что боты разные, — предложить, какой оставить, и что переписать:
секрет или состав чатов. Сам секрет не менять (нечем), только сказать какой и на что.

## ЗАДАЧА 2. Не дать секретам разъехаться снова

Сейчас ничто не мешает вписать в `TELEGRAM_MANAGER_CHAT_IDS` ссылку вместо номера
и узнать об этом через неделю по косвенным признакам.

Сделать проверку формы секретов частью обычного прогона, а не отдельной кнопки:

- `Telegram Chat Check` перевести с `workflow_dispatch` на расписание (раз в сутки
  достаточно) — падение проверки станет ранним сигналом;
- в `scripts/check-sync-freshness.mjs` перед отправкой проверять форму каждой
  записи тем же правилом, что и в `telegram-chat-check.py`, и писать в журнал
  понятную причину («в секрете не номер чата»), а не только ответ Telegram.

Правило формы вынести в один общий модуль и покрыть тестами, чтобы оно не
разошлось между двумя местами. Тесты — в шаг «Test scripts» в `ci.yml`.

## ЗАДАЧА 3. Второй канал для тревог (сначала предложение, потом код)

Пока Telegram сломан, тревога о протухшей занятости не доходит ни до кого: её
видно только как красный прогон в Actions. Неделю подряд занятость «Норы» не
обновлялась, и узнали об этом не из оповещения.

Нужен запасной канал. **Сначала описать варианты и дождаться решения Дарьи**,
код писать после. Обязательно учесть: репозиторий публичный, поэтому канал не
должен выносить наружу состав отелей и занятость (то есть GitHub Issues в этом
репозитории не подходят).

## ЗАДАЧА 4. Проверить отправку ваучеров тем же токеном

Карточка брони отправляет ваучер через `telegram-send-file.yml` в
`vars.TELEGRAM_BOOKING_CHAT_ID`. По прогону 12.09 этот чат боту недоступен, то
есть отправка, скорее всего, не работала ни разу. Проверить и починить (после
задачи 1 станет понятно, чинить токен или состав чата).

Отдельно: этот воркфлоу передаёт номер чата через блок `env`, а GitHub печатает
блок `env` в начале шага — номер попадает в публичный журнал при каждой отправке.
Предложить, как передать его, не засветив; не менять без ответа Дарьи, потому что
это уже на `main` и работает.
