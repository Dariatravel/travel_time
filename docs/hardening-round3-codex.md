## C1. Перевести синхронизации на транзакционную RPC (главная задача)

### Проблема
Все зеркала работают так: удаляют свои метки занятости, затем вставляют новые по одной,
**без транзакции**. Между удалением и последней вставкой номера выглядят свободными для
поиска, шахматки и Telegram-бота. Если вставка упадёт посередине — занятость потеряна
молча, а менеджер продаст занятый номер.

Места (все — один и тот же паттерн):
- `src/app/api/mirror/_lib/syncMirror.ts` — 4 ветки: `syncKontur` (:210-245),
  `syncIcal` (:370-405), `syncGoogleSheet` (:506-541), `syncShelter` (:640-692);
- `scripts/mirror-cron-sync.mjs` — iCal (:303-334), Shelter (:364-395);
- `scripts/bnovo-cron-sync.mjs` (:190-246);
- `scripts/googlesheet-cron-sync.py` (:306-341) — там же **результат DELETE
  отбрасывается**: провал неотличим от успеха;
- `src/app/api/realtycalendar/webhook/route.ts` (:316-346).

Образец правильной реализации, на который стоит равняться:
`src/app/api/realtycalendar/_lib/syncIcalFeeds.ts` — честный дифф, а не delete-all.

### Что делать
Готовая RPC уже написана: `public.sync_external_occupancy(p_source text, p_room_ids uuid[],
p_marks jsonb)` в `supabase/migrations/20260818204803_add_transactional_external_sync.sql`
— одна транзакция, advisory-lock, проверка пересечений с ручными бронями по ночам,
запись результата в `public.sync_runs`.

**Переводить по одному источнику за раз, за feature-flag.** Порядок от простого к сложному:
1. iCal reservationsteps (Аврора, Блэк Си, Грасс, Лазурит) — самый простой;
2. Google Sheets / WPS (Санрайз, Фемели, Вилла Леона);
3. Контур/bookonline24 (Вилла Оазис);
4. Bnovo через кабинет (Джаннат);
5. Shelter (Сан Амра, Нора, Студио) — последним, см. ниже;
6. RealtyCalendar webhook.

Для каждого источника в PR обязательно:
- прогон на копии: diff занятости по ночам против старого пути = **0 отличий**;
- подтверждение, что ручные брони и `manual_belvedere` не сдвинулись;
- запись появляется в `sync_runs`;
- добавить миграцию `20260818204803` в список в `scripts/apply-release-migrations.sh`
  (сейчас там стоит пояснение, почему её нет) — одновременно с первым переводом.

### Отдельно согласовать с владельцем до кода
`syncShelter` не только удаляет метки, но и **двигает ручные брони** менеджеров
(`computePullDownRepack`, `syncMirror.ts:651-661`), причём молча глотает конфликты.
Это противоречит правилу «ручные брони не трогать». Предложить владельцу: убрать
перемещение или сделать его явным и логируемым. **Не решать самостоятельно.**

### Ещё одна связка, требующая порядка
`webhook/route.ts` создаёт брони **без `external_source`** (:331-344, только `created_by`),
поэтому RPC считает их ручными и защищает. Если проставить метку раньше, чем перевести
этот путь на RPC, брони станут заменяемыми и могут быть затёрты. Сначала перевод, потом метка.

## C2. Внешние брони — только для чтения в интерфейсе

### Проблема
Сервер уже отклоняет правку внешних броней (`PATCH /api/yandex-backend/reserves/[reserveId]`
возвращает 403), но интерфейс об этом не знает: `external_source` не читается ни в форме
брони, ни в перетаскивании (проверено — упоминаний нет). Менеджер двигает метку зеркала,
получает ошибку либо правка молча затирается следующим прогоном крона.

- `src/features/BaseCalendar/lib/useReserveDragMove.ts` — запретить перетаскивание
  (сейчас гейт только по `is_fixed` и названию номера, :91-96);
- **override «Исключить вручную»**: действие с обязательной причиной, запись в аудит и
  флаг, который крон не перезатирает. **Модель согласовать с владельцем до реализации.**

Ориентир: в `src/features/OperationsCenter/ui/OperationsCenterPage.tsx:92-93` уже есть

## C3. Оповещения о поломке синхронизации — добить

`.github/workflows/sync-alerts.yml` уже шлёт сообщение менеджерам, но только когда крон
падает целиком. Не ловит два опасных случая:
- **частичный сбой**: воркфлоу «зелёный», а часть отелей не обновилась;
- **протухшие данные**: крон не запускался или источник молчит.

После появления записей в `sync_runs` (задача C1) добавить оповещение на:
- `status <> 'ok'`;
- отсутствие успешного прогона источника дольше N часов (N вынести в настройку).

## C5. Убрать N+1 при загрузке шахматки

`src/shared/api/hotel/hotel.ts:781/793` намеренно отдаёт номера с пустым списком броней,
после чего **каждая строка шахматки грузит свой запрос** (`src/app/main/reservation/page.tsx:68-71`,
рендер на каждый виртуальный элемент :504-527). Плюс серверный N+1: `hotel.ts:415-426`
делает по HTTP-запросу на каждый отель.

Сделать батч-эндпоинт: занятость по списку `hotelId` одним запросом.
**Важно:** батч обязан фильтровать отели по правам вызывающего (staff видит все, отельер —
только свои), иначе получится обход проверок, введённых в круге 2.
