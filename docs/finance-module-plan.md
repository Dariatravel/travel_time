## 1. Что я проверил в боевой базе (и что расходится с заданием)

### `hotel_scope` не существует

Задание говорит: «Часть уже реализована (`user_roles`, `hotel_scope`, API отельера)».
Таблицы, функции и даже упоминания в коде — **нет**. Доступ отельера сейчас держится
на `hotels.user_id` и проверках в каждом маршруте по отдельности
(например, календарный роут фильтрует `user_id = auth.uid()`).

Значит для кабинета отеля это работа **с нуля**, а не «достроить». Оценку это меняет.

### Предоплата хранится текстом

`reserves.prepayment` — тип `text`, не число. Из 8781 брони:

| Что лежит | Сколько |
|---|---|
| Чистое число | 7280 |
| Пусто | 1484 |
| Число с пробелами или точками | 9 |
| Отрицательные значения (`-8000`, `-18`, `-2`) | 8 |

Суммировать такое нельзя. Перед финансами поле нужно привести к числу — с решением,
что делать с отрицательными (возвраты? описки?) и с пустыми.

### Непонятно, что означает `reserves.price`

Поле `integer NOT NULL`, заполнено у 7270 броней. Но смысл плавает:

| Цена брони | Цена номера | Ночей | Если это «всего» → за ночь |
|---|---|---|---|
| 10000 | 10000 | 2 | 5000 |
| 17000 | 17000 | 12 | 1417 |
| 4000 | 4000 | 6 | 667 |
| 3250 | 4500 | 5 | 650 |

Часто цена брони равна цене номера — то есть похоже, что это **цена за ночь**,
скопированная из номера. Но тогда «17000 за 12 ночей» означало бы 204 000 с гостя,
что вряд ли. А если это «всего», то 1417 за ночь при цене номера 17000 — тоже странно.

**Это блокирующий вопрос.** Вся задача 1 стоит на «`guest_total` — сколько всего
с клиента». Пока неизвестно, что означает существующее поле, считать по истории нельзя.

### Метки автосинка — не брони

1441 запись из 8781 — это метки занятости из чужих календарей
(`external_source IS NOT NULL`), а не наши продажи. В расчёты они попадать **не должны**.
Ручных броней — 7340.

### Мелочи, которые всплывут в расчётах

- 249 броней короче одной ночи (заезд и выезд в один день) — деление на число ночей
  на них падает или даёт бесконечность.
- 1511 броней с ценой 0 — неясно, «не заполнено» или «бесплатно».
- Цены есть и в номерах: 2024 из 2407 номеров, максимум 25 000.

## 2. Доступ к финансам: предлагаю не трогать роли

### Чем плох вариант из задания

Задание предлагает добавить роль `owner` в CHECK и назначить её Дарье.
Проблема: **все существующие политики доступа проверяют `current_app_role()` на
`'admin'`**. Как только роль Дарьи станет `owner`, она перестанет быть админом —
и потеряет доступ ко всему остальному, пока каждую политику не перепишут.

Это прямо противоречит требованию задания «существующее поведение не менять»,
и радиус поражения — вся система разом.

### Что предлагаю вместо

Роли оставить как есть. Завести узкий список доступа к финансам:

```
app_private.finance_access (user_id uuid PRIMARY KEY, granted_by, granted_at)
public.has_finance_access() → boolean   -- SECURITY DEFINER, search_path=''
```

Все финансовые таблицы закрываются по `has_finance_access()`. Ничего из текущего
поведения не меняется — ни одна существующая политика не трогается.

**Почему это важно именно сейчас:** админов в системе **двое** —
`darya.tiande@gmail.com` и `incompleteness@ya.ru`. Требование «ни другие
администраторы» выполняется сразу и без переделки ролей.

Побочная выгода: позже можно дать доступ бухгалтеру, не делая его админом.

## 3. Уточнения к схеме (черновик задания в целом рабочий)

- **Деньги — `numeric(12,2)`**, не `float` и не `integer`. Копейки целыми числами тоже
  можно, но `numeric` читается в отчётах без пересчёта.
- **Валюта.** Если когда-нибудь появятся расчёты не в рублях — колонку лучше завести
  сразу, добавлять потом больно. Вопрос владельцу.
- `reserve_settlements` — одна строка на бронь (`UNIQUE (reserve_id)`), и защита от
  расчётов по меткам автосинка: они не наши продажи.
- **История изменений** — по образцу `reserve_history`
  (`id, reserve_id, action, changed_by, changed_at, changes jsonb`). Не изобретать своё.
- Суммы считать в SQL — согласен с заданием. Предлагаю представления (`view`) для сводки
  по отелю, чтобы интерфейс не пересчитывал.
- Тесты на крайние случаи: ноль ночей (**есть 249 таких броней**), выезд раньше заезда,
  нулевая сумма, отрицательная предоплата (**есть 8**), бронь без отельера
  (**2 отеля из 237 без владельца**).

## 4. Порядок, который предлагаю

Отличается от задания только началом: сперва ответы, потом схема.

1. **Ответы на вопросы ниже** — без них схема будет переделываться.

   с откатом (приём отработан).
4. Финансовые таблицы + RLS + история.
5. Экран финансов для владельца.
6. Цены: сначала **посмотреть вкладку «цены»**, потом схема `price_rules` и импорт с логом.
7. Кабинет отеля с финансовой историей.
8. Проверка, что менеджер не видит финансы — на уровне базы, а не интерфейса.
